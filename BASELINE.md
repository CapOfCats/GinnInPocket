# BASELINE: Многоагентный Telegram‑ассистент

## 1. Назначение и область применения

Данный проект представляет собой многоагентную интеллектуальную систему, интегрированную с мессенджером Telegram.  
Система предназначена для сбора параметров пользователя, проведения автоматизированного поиска подходящих вариантов во внешних источниках, их валидации по заданным критериям и предоставления пользователю итоговой подборки в человекочитаемом виде.

Основные задачи проекта:
- автоматизировать диалоговый сбор требований и предпочтений пользователя;
- формировать структурированную анкету на основе естественно‑языковых сообщений;
- осуществлять поиск релевантных альтернатив во внешних источниках;
- реализовывать многошаговую проверку найденных вариантов (логическая и целевая/бюджетная);
- возвращать пользователю понятный и обоснованный результат через Telegram.

---

## 2. Архитектура и основные компоненты

Архитектура проекта построена по принципу конвейера из специализированных агентов.  
Каждый агент решает свою подзадачу и передаёт результат следующему компоненту.

### 2.1. Основные компоненты системы

| Компонент              | Тип           | Основная роль                                         |
|------------------------|--------------|-------------------------------------------------------|
| Telegram‑интерфейс     | Внешний слой | Приём/отправка сообщений, идентификация пользователя |
| Router                 | Оркестратор  | Маршрутизация запросов между агентами и хранилищем   |
| Анкетёр (Form Agent)   | Агент        | Диалоговый сбор и первичное заполнение анкеты        |
| Clarifier              | Агент        | Нормализация данных, уточнение, подготовка payload   |
| Researcher             | Агент        | Поиск внешних вариантов и формирование карточек      |
| Validator              | Агент        | Внутренняя и внешняя проверка альтернатив            |
| Хранилище (таблица/БД) | Данные       | Состояние анкеты и служебная информация              |

## 3. Сквозной поток обработки запроса

Ниже описан типовой жизненный цикл одного пользовательского запроса.

### 3.1. Текстовая схема потока

Пользователь (Telegram)  
→ Telegram Bot → Router → (проверка анкеты в хранилище)  

- если анкета не заполнена:  
  Router → Анкетёр → Хранилище → Router → Clarifier  

- если анкета уже есть:  
  Router → Clarifier → Researcher → Validator → Clarifier → Пользователь (Telegram)

### 3.2. Этапы обработки

1. **Инициация диалога**  
   Пользователь отправляет сообщение боту в Telegram. Telegram‑интерфейс принимает сообщение и передаёт его в Router.

2. **Маршрутизация в Router**  
   Router извлекает идентификатор пользователя (например, `chat_id`), выполняет запрос в хранилище для поиска существующей анкеты и, в зависимости от результата, либо запускает Анкетёра, либо передаёт управление Clarifier.

3. **Сбор анкеты (Анкетёр)**  
   Анкетёр ведёт диалог с пользователем, уточняет цели, бюджет, ограничения и другие параметры и сохраняет результаты в хранилище в виде строки анкеты.

4. **Нормализация и уточнение (Clarifier)**  
   Clarifier считывает анкету из хранилища и последние сообщения пользователя, выделяет сущности, нормализует данные, при необходимости формирует уточняющие вопросы и после завершения уточнений подготавливает структурированный payload для Researcher.

5. **Поиск альтернатив (Researcher)**  
   Researcher получает payload, формирует поисковые запросы к внешним источникам, отбирает несколько (5–7) релевантных вариантов, приводит их к виду карточек и передаёт их вместе с контекстом пользователя в Validator.

6. **Валидация альтернатив (Validator)**  
   Validator получает карточки и текущую анкету пользователя, проводит внутреннюю и внешнюю проверку каждого варианта, формирует структурированный JSON со статусами и пояснениями и возвращает его в Clarifier.

7. **Формирование итогового ответа (Clarifier)**  
   Clarifier на основе решения Validator’а формирует человекочитаемое сообщение и отправляет итоговый ответ пользователю через Telegram‑интерфейс.

## 4. Роли агентов и ответственность

### 4.1. Обобщённая таблица ролей

| Агент / компонент | Входные данные                         | Основные действия                                                       | Выходные данные                                      |
|-------------------|-----------------------------------------|-------------------------------------------------------------------------|------------------------------------------------------|
| Router            | Сообщения из Telegram, данные анкеты    | Определяет сценарий, запускает нужных агентов                          | Команды запуска агентов, маршрутизация payload       |
| Анкетёр           | Сообщения пользователя, черновая анкета | Ведёт диалог, задаёт вопросы, собирает параметры                       | Обновлённая анкета в хранилище                       |
| Clarifier         | Анкета, сообщения, технический контекст | Нормализует данные, уточняет, готовит payload, формирует финальный ответ | Нормализованный payload; итоговый текст для пользователя |
| Researcher        | Нормализованный payload                 | Формирует поисковые запросы, выбирает релевантные варианты             | Набор карточек вариантов                             |
| Validator         | Карточки, анкета пользователя           | Выполняет внутреннюю и внешнюю проверку, присваивает статусы           | Структурированный JSON с оценкой вариантов           |
| Хранилище         | Данные от агентов                       | Сохраняет и предоставляет состояние анкеты                             | Актуальная анкета и служебные данные                 |

### 4.2. Telegram‑интерфейс и Router

Ответственность: интеграция с Telegram‑Bot API, приём и отправка сообщений, маршрутизация сообщений к соответствующим агентам на основе состояния анкеты, взаимодействие с хранилищем (чтение/создание/обновление строк).

### 4.3. Агент сбора анкеты (Анкетёр)

Ответственность: проведение диалога первого уровня, уточнение целей и базовых параметров, первичное заполнение или существенное обновление анкеты пользователя и сохранение её в хранилище.

### 4.4. Clarifier

Ответственность: нормализация и структурирование данных анкеты, разрешение неопределённостей через уточняющие вопросы, подготовка payload для Researcher и формирование финального ответа на основе решения Validator’а.

### 4.5. Researcher

Ответственность: генерация поисковых запросов по нормализованной анкете, обращение к внешним источникам, подбор релевантных альтернатив и преобразование результатов поиска в однородные карточки.

### 4.6. Validator

Ответственность: сопоставление карточек вариантов с анкетой пользователя, внутренняя и внешняя проверка, присвоение статусов и формирование аргументированного итогового решения.

## 5. Хранение данных и структура анкеты

Система хранения реализуется в виде табличной структуры (например, Google Sheets или аналогичная таблица/БД).  
Каждая строка описывает одного пользователя или один логический запрос.

### 5.1. Пример структуры таблицы анкеты

| Поле                   | Тип            | Назначение                                               |
|------------------------|----------------|----------------------------------------------------------|
| id                     | Целое / строка | Внутренний идентификатор записи                         |
| chat_id                | Строка         | Идентификатор пользователя в Telegram                   |
| user_name              | Строка         | Имя/логин пользователя (если доступно)                  |
| goals                  | Текст          | Цели пользователя, сформулированные Анкетёром/Clarifier |
| budget_min             | Число          | Минимальный бюджет                                      |
| budget_max             | Число          | Максимальный бюджет                                     |
| constraints            | Текст          | Ограничения и предпочтения                              |
| questionnaire_status   | Строка         | Статус анкеты (черновик/заполнена/нужно уточнение)      |
| last_request_timestamp | Дата/время     | Дата последнего обращения                               |
| last_state             | Строка         | Текущее состояние диалога/воркфлоу                      |

## 6. Структуры данных и обмен между агентами

Для взаимодействия между агентами используются JSON‑структуры.

### 6.1. Payload Clarifier → Researcher

Пример полей:

- `user_id` — идентификатор пользователя;  
- `goals` — нормализованное описание цели;  
- `budget.min` и `budget.max` — диапазон бюджета;  
- `constraints` — ключевые ограничения и предпочтения;  
- `context` — дополнительный контекст.

### 6.2. Payload Researcher → Validator

Пример полей:

- `user_id` — идентификатор пользователя;  
- `options[]` — массив карточек, где у каждой:
  - `option_id` — идентификатор варианта;
  - `title` — название;
  - `url` — ссылка на источник;
  - `price` — цена;
  - `summary` — краткое описание;
  - `attributes` — словарь дополнительных характеристик.

### 6.3. Payload Validator → Clarifier

Пример полей:

- `user_id` — идентификатор пользователя;  
- `approved_options[]` — список одобренных вариантов с полями:
  - `option_id`, `status`, `score`, `internal_comment`, `external_comment`;  
- `rejected_options[]` — список отклонённых вариантов с теми же полями статуса и комментариев;  
- `overall_comment` — общий комментарий и вывод по результатам проверки.

## 7. Технические особенности реализации

- Взаимодействие с пользователем осуществляется через Telegram‑бота, который обеспечивает транспорт сообщений и идентификацию пользователя.  
- Обработка естественного языка и принятие решений выполняются специализированными агентами, использующими модели машинного обучения.  
- Воркфлоу имеет модульную структуру: каждый агент реализует отдельный шаг конвейера и оперирует чётко определёнными структурами данных.  
- Централизованное хранилище в табличном формате используется для хранения анкеты и профиля пользователя, отслеживания состояния обработки и последующего анализа качества работы системы.
